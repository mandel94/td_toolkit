# Dashboard Architecture Documentation

## 🏛️ Architectural Patterns Applied

This dashboard implements several design patterns following 2025 best practices:

### 1. Facade Pattern
**Location**: `data/ga4_client.py`

The `GA4ClientFacade` class abstracts the complexity of the Google Analytics 4 API:
- Simplifies authentication
- Provides clean methods for common operations
- Hides implementation details from business logic

### 2. Repository Pattern
**Location**: `data/repositories.py`

Repositories isolate data access from business logic:
- `AnalyticsRepository`: Base repository for data access
- `CachedAnalyticsRepository`: Adds caching layer

Benefits:
- Easy to mock for testing
- Can swap data sources without affecting services
- Centralized data access logic

### 3. Service Layer Pattern
**Location**: `services/`

Services contain business logic:
- `AnalyticsService`: Coordinates data operations
- `TrendService`: Implements trend analysis algorithms

Benefits:
- Separates business logic from data access
- Reusable across different UI components
- Easy to test independently

### 4. Strategy Pattern
**Location**: `strategies/aggregation.py`

Different aggregation strategies can be selected at runtime:
- `DailyAggregation`
- `WeeklyAggregation`
- `MonthlyAggregation`

Benefits:
- Extensible: easy to add new aggregation types
- Follows Open/Closed Principle
- Clean interface for switching algorithms

### 5. Factory Pattern
**Location**: `ui/components.py`, `strategies/aggregation.py`

Factories create objects:
- `ComponentFactory`: Creates UI components
- `ChartFactory`: Creates Plotly charts
- `AggregationFactory`: Creates aggregation strategies

Benefits:
- Centralized object creation
- Easier to maintain and extend
- Consistent component styling

### 6. MVC-Inspired Separation
**Location**: `ui/` directory

- **Model**: Services and repositories (`services/`, `data/`)
- **View**: Layout and components (`ui/layout.py`, `ui/components.py`)
- **Controller**: Callbacks (`ui/callbacks.py`)

Benefits:
- Clear separation of concerns
- Easier to modify UI without touching logic
- Better testability

## 📊 Data Flow

```
User Interaction
    ↓
Dash Callback (callbacks.py)
    ↓
Service Layer (analytics_service.py, trend_service.py)
    ↓
Repository (repositories.py)
    ↓
GA4 Client Facade (ga4_client.py)
    ↓
Google Analytics 4 API
    ↓
Response flows back up the chain
    ↓
UI Components rendered
```

## 🔄 Key Workflows

### 1. Dashboard Update Workflow

1. User clicks "Aggiorna Dati" button
2. Callback in `callbacks.py` triggered
3. Callback calls `analytics_service.get_trend_data()`
4. Service uses `repository.get_page_views_by_period()`
5. Repository calls `ga4_client.fetch_page_views_trend()`
6. Data returned and transformed through layers
7. Trend analysis applied by `TrendService`
8. Insights generated by `InsightGenerator`
9. UI components created and returned to Dash

### 2. Aggregation Strategy Selection

1. User selects granularity (daily/weekly/monthly)
2. `AggregationFactory.create_strategy()` called
3. Appropriate strategy instance returned
4. Strategy applied to raw data
5. Aggregated data displayed

## 🧩 Extension Points

### Adding New Metrics

1. **Data Layer**: Extend `ga4_client.py` to fetch new metric
2. **Repository**: Add method to `repositories.py`
3. **Service**: Add business logic in `analytics_service.py`
4. **UI**: Create component in `components.py`
5. **Callback**: Wire up in `callbacks.py`

### Adding New Visualizations

1. Add method to `ChartFactory` in `components.py`
2. Call from callback in `callbacks.py`
3. Add to layout in `layout.py`

### Adding New Insights

1. Extend `InsightGenerator` in `insights/insight_generator.py`
2. Call from callback
3. Display using `ComponentFactory.create_insight_box()`

## 🎯 SOLID Principles Applied

### Single Responsibility Principle
Each class has one reason to change:
- `GA4ClientFacade`: Only changes if GA4 API changes
- `AnalyticsService`: Only changes if business logic changes
- `ComponentFactory`: Only changes if UI components change

### Open/Closed Principle
Open for extension, closed for modification:
- New aggregation strategies can be added without modifying existing ones
- New insights can be added without changing core generator

### Liskov Substitution Principle
Subclasses can replace parents:
- `CachedAnalyticsRepository` can replace `AnalyticsRepository`
- Any `AggregationStrategy` subclass works in the factory

### Interface Segregation Principle
Clients depend on specific interfaces:
- Services only use repository methods they need
- Callbacks only call specific service methods

### Dependency Inversion Principle
Depend on abstractions, not concretions:
- Services depend on repository interface
- Callbacks depend on service interface

## 🔒 Design Decisions

### Why Dash over Streamlit?
- Better component reusability
- More control over callbacks
- Production-ready out of the box
- Better performance for real-time updates

### Why Caching Repository?
- Reduces API calls to GA4
- Improves dashboard responsiveness
- Easy to implement with decorator pattern

### Why Strategy Pattern for Aggregation?
- Makes it trivial to add new time granularities
- Clean separation of aggregation logic
- Testable in isolation

### Why Facade for GA4?
- GA4 API is complex
- Provides clean interface for common operations
- Easy to mock for testing
- Encapsulates authentication logic

## 📈 Performance Considerations

1. **Caching**: In-memory cache reduces API calls
2. **Lazy Loading**: Data fetched only when needed
3. **Efficient Aggregation**: Pandas vectorized operations
4. **Minimal Redraws**: Dash only updates changed components
